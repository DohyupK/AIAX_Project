# JH 프론트 — PC 최적 UI · 모바일 최적 UI 규격

- 대상: `JH/frontend/pages/**`, `JH/frontend/common/**`의 UI·CSS·레이아웃
- 작성: DH (JH 승인). 에이전트(클로드 포함)가 JH 화면을 만들·바꿀 때 **필수**
- 상위 강제: 루트 [`AGENTS.md`](../../AGENTS.md) 「5-2. JH 프론트 — PC 최적 UI·모바일 최적 UI」

## 원칙

1. **PC 최적 UI**와 **모바일 최적 UI**를 **같은 작업에서 둘 다** 구현한다.
2. 한쪽만 만들면 **미완료**. 사용자가 모바일을 말하지 않아도 모바일을 빼지 않는다.
3. PC 레이아웃을 찌그러뜨려 “안 깨지게만” 한 것은 모바일 최적이 **아니다**.
4. 별도 URL 강제 아님. 동일 컴포넌트 + `@media`(또는 동등한 반응형)로 결과를 맞춘다.
5. 루트 `app/`·사이드바 셸은 DH 문의. 이 규격은 **페이지 본문** 기준이다.

API·순수 데이터·문서만 수정하면 이 규격을 적용하지 않는다.

## 뷰포트

| 구간 | 기준 | 역할 |
|------|------|------|
| PC | 대략 1280px+ | PC 최적 구성·밀도 |
| 좁은 창·태블릿 | `max-width: 860px` | 다단 → 1열 또는 접힘, 모바일용 정보 순서 |
| 폰 | `max-width: 460px` | 패딩·글자·터치 영역 |

페이지에 이미 900px 등 다른 끊음이 있어도, **최소 860px 이하에서 1열화(또는 접힘)** 는 반드시 성립해야 한다.

---

## PC 최적 UI — Pass (모두 충족)

| # | 조건 |
|---|------|
| P1 | 넓은 뷰포트에서 정보 밀도·다단 배치를 의도적으로 쓴다. PC 화면이 “불필요하게 1열만인 축소판”만으로 끝나지 않는다. |
| P2 | 사이드-메인, 카드 그리드, 툴바+본문 등 PC용 구성이 겹침·잘림 없이 읽힌다. |
| P3 | 표·차트·패널이 PC 폭을 활용한다. 가로로만 빈 여백이 남는 레이아웃이 주가 되지 않는다. |

---

## 모바일 최적 UI — Pass (모두 충족)

| # | 조건 |
|---|------|
| M1 | `max-width: 860px`에서 다단은 1열 또는 접힘으로 **모바일용 정보 순서**가 된다. PC 레이아웃을 그냥 찌그러뜨린 상태가 아니다. |
| M2 | `max-width: 460px`에서 패딩·글자·터치 영역이 폰 사용에 맞게 조정된다. |
| M3 | 페이지 단위 가로 스크롤이 없다. 넓은 표·차트만 **래퍼 안**에서 가로 스크롤을 허용한다. |
| M4 | 고정 `px` 폭으로 본문이 잘리지 않는다. 본문은 `max-width: 100%` / `minmax(0, 1fr)` / `%` 등으로 줄어든다. |
| M5 | 해당 페이지의 주요 버튼·필터·탭·입력이 좁은 폭에서도 보이며 조작 가능하다. |
| M6 | 이번 변경 CSS에 `@media`(또는 공통 반응형 유틸 연결)가 **실제로** 있다. “모바일 후속” 주석만으로 끝내지 않는다. |

---

## Fail (하나라도 해당하면 미완료)

- PC만 구현하고 860/460 대응이 없다.
- 모바일은 “안 깨지게만” 축소하고, 스택·접힘·터치 등 모바일 구성이 없다.
- 모바일만 맞추고 PC에서 다단·밀도 없는 1열만 강제한다.
- “반응형 예정” 주석만 있고 `@media`(또는 동등 처리)가 없다.
- 좁은 폭에서 본문 잘림, 페이지 단위 가로 스크롤, 겹침으로 주요 기능 사용 불가.

---

## 자가 점검 (작업 종료 전)

| 구분 | 폭 | 확인 |
|------|-----|------|
| PC | 1280 (및 대상 화면의 넓은 폭) | P1~P3 예/아니오 |
| 모바일 | 360, 390, 768 | M1~M6 예/아니오 |

브라우저를 열 수 없으면 CSS·마크업만으로 위 조건이 성립하는지 **근거를 남긴다**.  
**PC Pass와 모바일 Pass를 모두 통과하기 전에는 해당 UI 작업을 완료로 치지 않는다.**
